## Current architecture (high level)
### Core runtime
- `Simulation` orchestrates SimPy execution and uses an `EffectEngine` to apply `UnitaryEdit` batches.
- `Operation` instances produce edits via `get_operation_effects()`.
- `OperationSelector` picks next operations based on a query graph.

### Knowledge graph + validation
- Canonical state is a KG built from ontology-backed Pydantic objects.
- Correctness can be enforced with SHACL validation.

### Overlays
- Overlays are generated by “overlay providers” (e.g., current volume, SPPT skeleton).
- The engine currently builds overlay/union graphs by materializing copies, which can become expensive.

### Endogenous behavior
- Spawners subscribe to lifecycle events and can generate endogenous operations.
- Policy/remediation/reporting exist to support closed-loop diagnosis/repair.

## Known hotspots / risks (to address in this refactor)
1) Union graph creation and overlay graph creation are currently copy-heavy (risk of O(steps × graph_size)).
2) `SPPTOverlayProvider.snapshot()` rebuilds a full graph from stored spans each time (risk of O(N²) across a run).
3) Operation authoring is still “list of atomic edits” heavy; we want a DSL/macros layer without exposing arbitrary atomic RDF manipulation.
4) Debuggability: SHACL failures should be easier to interpret (human-readable effect summaries).

## Refactor objectives (Path A)
- Reduce per-step overhead by using union graph “views” rather than copying triples.
- Make SPPT overlay incremental (O(1) snapshot; O(ops) overall).
- Add an operation-effects DSL (macros/builder) that emits existing `UnitaryEdit`s.
- Improve diagnostics (describe edits/operations in report output).
- Add docs/examples so new users can extend via Operations/Spawners without touching engine internals.
